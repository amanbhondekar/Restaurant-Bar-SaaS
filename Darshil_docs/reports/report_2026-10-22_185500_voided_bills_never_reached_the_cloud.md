# Voided bills could never reach the cloud

**Date:** 2026-10-22T18:55:00+05:30
**Branch:** `feat/m2-kitchen-ops`
**Scope:** a bug in the billing replication, found by the cloud contract work; a flaw in that work's own test

---

## THE BUG

The hub records a voided bill as `payment_status: 'voided'`. Migration 005's CHECK constraint on
`invoices.payment_status` allows `'pending', 'paid', 'void', 'refunded', 'split'` — **`void`, not `voided`**.

The row builder passed the hub's word straight through. So **every voided bill's push would have been refused by
the constraint, on every attempt**. The consequence is worse than a stuck item: a bill the cloud already held as
*pending* or *paid* (it is pushed at every state change) would **stay that way in the cloud**, still counted as
revenue, after the restaurant had voided it. A cloud ledger that includes bills the owner reversed is exactly the
failure replication exists to prevent. Ledger *repair* would have the same blind spot: the hub wins every conflict,
but a void it could never push never became visible.

It had not bitten because **no real project has ever received a push** — which is also why a fake could not show it.

## HOW IT WAS MISSED, AND HOW IT WAS FOUND

The cloud contract test (previous report) held every row the hub builds against the migrations' schema and
reported "every row matched". It was **wrong to say so**. Its sample bills were written by hand, with
`payment_status` taken from the SQL's own list — so it fed the constraint the constraint's own word and, of course,
it fit.

It surfaced while reading the ledger code for the analytics work: `reconciliation.js` tests
`payment_status === 'voided'`. Driving the **real invoice store** through every state confirmed what it writes:
`pending`, `paid`, `refunded`, `voided`, and a split that settles as `paid` with method `split`.

## THE FIX

At the cloud boundary, in `invoiceSync.js`: `toCloudStatus('voided') → 'void'` on the way up and
`fromCloudStatus('void') → 'voided'` on the way down (restore and ledger repair). Nothing else is translated. The
cloud keeps the vocabulary its migration defined, and **no migration has to be run** — which matters, because
migration 005 may or may not have run anywhere. `cloud:check`'s probe bill now uses the hub's word and checks it
comes back as the hub's word.

## THE TEST, MADE HONEST

- **Bills are now generated by the real invoice store** (issue, pay, refund, void, split and settle), and every one
  is held against the table. This is the test that would have caught it; **it was run against the unfixed code
  first and failed**, then passed after the fix.
- A voided bill goes up as `void` and comes back as `voided`; **every real state survives the trip to the cloud and
  back with its status intact**.
- The reservation and walk-in statuses now come from **the hub's own exported lists**, not copies from the SQL —
  the same mistake, closed everywhere the contract test had it. (They matched the CHECKs already.)
- **Mutation-checked, 5:** each half of the translation removed, each call site bypassed, and a translation that
  fires on everything. All caught.

Full hub suite: `1046 passed`.

## WHAT THIS CHANGES ABOUT THE EARLIER CLAIM

The billing-replication report said the contract check "found them all consistent". That was true of what it
checked and **not** true of the cloud, and the roadmap now says so: the contract test proves the *columns, required
columns, unique indexes and CHECK values for the states it is given*; **the states it is given must come from the
hub, not from the schema**. That rule is now the test's own header.

## WHAT IS NOT DONE

Still nothing has run against a real Supabase project, and row-level security is still proven by nothing. This is
one more reason to run `npm run cloud:check -- --probe <restaurant>` the day a project exists: a probe bill is
written in the hub's vocabulary, so it exercises this exact path.
