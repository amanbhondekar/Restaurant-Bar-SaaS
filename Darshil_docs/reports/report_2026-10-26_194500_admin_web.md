## WHAT CHANGED

`admin_web/` is the founders' console as a page: a static build on its own host (invariant I10), reusing the product's design tokens and fonts and two screens of the operator console. With the database spine and the API (`report_2026-10-26_173000_admin_console_phase1_foundation.md`) it completes Phase 1's parts.

- **Sign-in and the second factor** (`src/lib/auth.js`, `src/screens/AuthScreens.jsx`): email and password with Supabase Auth; first time, an authenticator app is set up (a QR code, and the setup key to type if scanning is not possible); after that, a 6-digit code. The page is "ready" only at the second level (`aal2`); anything it cannot read is "signed out".
- **The gate** (`src/AdminApp.jsx`): once the session is at `aal2` the API is asked who they are; a non-administrator is told so and shown nothing else; the sign-in is **recorded before the console is shown** (an unrecorded sign-in is not a sign-in); a second-factor refusal from the API sends them back to the code; a refused session ends it.
- **The console** (`src/screens/Console.jsx`): Fleet (the operator console's screens, read again every minute, one read at a time, with an "as of" stamp, ageing between reads, and a banner that marks what is shown as older when a read fails) and a restaurant's page.
- **The audit log** (`src/screens/AuditPage.jsx`): filter by restaurant, event type, source and dates (the last day included); page back without showing an event twice; export a CSV; check the integrity of a restaurant's history or the console's own, with the verdict dropped the moment the question changes. A search superseded by a newer one is dropped when it arrives.
- **The client** (`src/lib/api.js`): the token in a header only (never an address, never stored); cookies off; no caching; no referrer; every failure becomes one of a few kinds the screens word. The server's own words are shown only for a 400, which the API writes for a person.
- **Settings and build** (`src/lib/config.js`, `vite.config.js`, `vercel.json`, `.env.example`): three public settings; the build refuses a service key (by name or by what the value says it is), an address that is not https (the API may be http on this machine), or an address with a path or credentials; it writes a content-security policy naming exactly the two places the page may talk to; the host sends the framing, sniffing, referrer, HSTS, permissions and no-cache headers.
- `package.json`: `npm run admin:web` (development, :5174) and `npm run build:admin` (the build); `vitest.config.js` includes `admin_web/test`.

**Not part of this change:** the CSS fix below, which is its own commit and report (`report_2026-10-26_190000_design_system_button_layer.md`).

## WHAT THE TESTS PROVE

Written first. **165 page tests in 6 files** (Vitest and Testing Library) and **13 build-level tests**; the frontend suite is now 1277 tests (the product's own 1112 plus 165), and the hub suite 2041.

- `AdminApp` (sign-in, the second factor, the gate, leaving): the order of what happens; that nothing of the console is shown before every step is done; failures worded in plain sentences, with the text of an error not written for a person never shown; the password cleared after a failure; a double submit sending one request, and React's double-run of effects (StrictMode) recording the sign-in and making the second factor once; a code sent as six digits and only as six digits; a notice that belongs to one sign-in not following someone through the next; and nothing written to storage, cookies or the address through a whole sign-in.
- `Console`: the fleet as text whatever the names contain; reads one at a time; a failed read marked as older with the time it was read; a failed first read showing nothing; the way between places; and that no control on the page can change anything.
- `AuditPage`: filters sent as asked and no others; paging without duplicates; stale searches dropped; export once; verdicts dropped when the question changes or arrives late; payloads and names drawn as text.
- `api`, `auth`, `config`: the client's every route, header and failure kind; the auth adapter against a fake of Supabase's client, and the real library once (nothing is written to browser storage); the settings' refusals.
- `adminWebBuild` (13, node): runs the **real production build** and checks that the page is styled (a stylesheet with the tokens, the two fonts and a class only the reused screens use, which proves the build looked in `../src` too), has exactly one script and one stylesheet and no inline script, carries the exact policy, ships the product's fonts and no other page, service worker, manifest or source map, holds none of the product's other screens, and names no service key; and that the build refuses a service key or an unsafe address. These exist because the page tests run without CSS: a past split of a file dropped a stylesheet import with every test green.

**Mutation checking: 179 mutants** across the API client, the auth adapter, the settings, the formatting, every screen, the Vite config and the stylesheet. **151 were caught at first; 28 survived.** Of those, 26 were gaps in the tests (closed: error-status edge cases, auth-state edge cases, double submits that only a guard can stop because the button is disabled too late for them, StrictMode, a stale notice, restaurants reaching the audit page, and others), 2 had been run against the wrong test file, and **1 was a redundant line, removed** (clearing the notice on sign-in: every other path back to the sign-in form sets or clears it). On the re-run **all were caught**.

## LOOKED AT IN A REAL BROWSER

The production build, served; the sign-in page in light and dark and at phone width; a sign-in attempt against an address that cannot resolve (which showed a styled error, cleared the password, kept the email, and left browser storage empty, with the only console message the expected DNS failure and no policy violation). The console screens (fleet, a restaurant, the audit log with a history check, and the enrolment screen) were looked at through a throwaway harness with fake data, since deleted. **That found the design-system fault** in the other commit.

## HONEST LIMITS

- **It has never met a real Supabase project.** The sign-in, the second factor and the QR code are proven against a fake of Supabase's client and, for storage, against the real library with no network. A QR code from the real service has never been drawn; the policy permits `data:` images for it.
- **The console screens were seen with fake data**, not with the real API.
- Sessions are in memory only, so a refresh asks for the password and a code again. That is chosen, not an oversight.
- The API's address and Supabase's are baked into the build; changing either means a new build.
- **`OPS_TOKEN` is not retired**: it stays as the break-glass until the page has run against a real project.
- JWKS support in the API covers RSA and P-256 keys, which is what Supabase issues.
- The kitchen display's connection-light test (`src/test/kitchen/KitchenDisplay.test.jsx`) failed intermittently while this was being finished. The cause found was mine: the real Supabase client, used once in a test, started a token-refresh timer that fired after its file's browser environment was gone (an unhandled "window is not defined"). The test now stops it, and four full runs in a row passed. The kitchen test is timing-sensitive (real and fake clocks together) and may still be flaky under heavy load; it is not changed.
